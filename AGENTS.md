# AGENTS.md

## Hard rules
- **Where colours land.** Line under panes is `app.info` (green) and `app.error` (yellow), expiring through `App::live_msg`; nothing there or in statusline ever red. Red only for what is about to change or be lost: `Mode::Edit` indicator, rows marked for deletion (also crossed out), delete lines of `:changes`, any gate added later. Failure too long for that line goes through `App::fail` into yellow alert box.
- **Never add dependency needing C library, system headers or external binary.** `cargo install vibox` must succeed on bare toolchain; build failing on missing header is broken product. Hence audio output written against pulseaudio wire protocol, not cpal.
- **Published crate has lib target; lib is not public API.** It exists only so `tests/` and `examples/` reach code (see Overview), not so anyone depends on `vibox` as library, so `pub` item moving or changing shape is not breaking, needs no major bump. Never treat module paths as contract.
- **vibox never retags a track; touches music folder only as user asked:** rename typed in edit buffer, move, copy, delete or `:mkdir`. Everything else about library read only. README promises this in three sections (`Rename files in place`, `Nothing is written until :w`, `Changing the library itself`), so feature widening it without widening those is documentation lie as well as bug.
- **No arming switch in front of file operations; never add one.** Staging is the guard: nothing touches disk on keypress, `:ch` lists what waits, `u` and `:e!` undo it, `:q` refuses while anything pending, so only way to lose file is read change and type `:w`. Mode set once and forgotten protects nothing a readable staged change does not. Stronger guard, if ever wanted, goes at destructive commit (red gate on `:w` that deletes), never in a mode.
- **Unknown option skipped, not fatal.** `:set` reports unknown name and carries on with rest of line, so one stale word in rc file cannot cost options beside it; `load_rc` clears message afterwards, so file is silent and person typing is not.
- **`:w` planned before applied** (`app::plan`, entered through `App::write_plan`): renames, moves, copies, deletions checked together as one namespace, because per-kind checks each see only own list, so refuse rename onto name a deletion frees and let rename and move claim one name, where `fs::rename` silently overwrites one with other. **occupied** asked of filesystem, without following symlinks so dangling link still counts as file, never of `app.tracks` (holds only audio, so would clobber `cover.jpg`; on case-insensitive mount `song.mp3` and `SONG.mp3` are one file, two strings); in-memory sets may only excuse clash, never invent one. Name batch frees under one spelling is free under another when disk says both are one name (`write::case_alias`: one folder, names equal but for case, one file, folder lists only one of two spellings), which hard link with own name never is; two claims in folder that tells names apart without case (`write::folds_case`, asked of disk) are one claim. Nothing may land inside folder marked for deletion, since folders go last and take whatever landed in them; marking folder something waits to land in refused at `dd`; landing on folder's own name fine, runs once folder gone. Order worked out across every kind at once from what each step frees, takes and reads: whatever frees name runs before whatever lands on it, copy runs before its source goes, whatever starts inside deleted folder runs before folder goes, everything inside folder runs before folder's rename; cycle (swap) refused, not given temporary name, as is any plan that cannot place every step, whichever step stuck. Also refused before anything runs: file leaving by two steps, and source not on disk that no step puts there (`App::write_plan`), since either stops write halfway. `App::start_write` (`app/write.rs`) runs exactly those steps in that order on own thread, guarding every rename and move right before call, since plan is a moment old and `fs::rename` overwrites without asking; closing last microsecond needs `renameat2`, needing libc and `unsafe`, so window stays open. Copy never overwrites (`create_new`) and removes half-made file if it stops. Case-only rename on disk ignoring case goes through spare name in same folder, because there both names are one file and renaming file onto itself does nothing. Thread touches only disk: input thread lands each step's report (`App::write_landed`), so memory follows disk step by step, folder list included, so open folder stays open under new name. Failure no check foresees (permission, full disk) stops write at that step: what ran stays done, rest stays pending, message says which.
- **Typed name checked when its buffer is left** (`App::commit_name`): not empty; no `/`, since this renames, never moves; no leading `.` on track or folder, since vibox lists no hidden file; for playlist, name no other playlist has under either extension or is waiting to get (`App::playlist_named`). Bad one refused there, old name kept, so never reaches write that would leave folder half renamed, and `:w` with bad name in buffer writes nothing, so refusal stays readable. Whether name is *free* is plan's job, only thing seeing deletions and moves that free one; exception: row already moving or being copied (`App::is_staged`, never `origin_of` differing from path: copy back onto name its file leaves reads own path), whose new name becomes part of destination and is checked like a put.
- **Each file has one pending step from disk to where it ends.** Moving row already moving or being copied changes that step, not adds one (`App::pend_move`); several rows put at once have every row and step found before any moves (`App::move_rows`), since one can land on name another leaves; copy reads file where it is on disk now (`App::origin_of`), so `copies` holds disk paths only; renaming moved or copied row changes destination; chain of steps claims one name twice, which `:w` refuses. What `:w` does is worked out from rows (`App::file_batch`, which `:ch` lists too), never from order of actions: row marked for deletion deletes file it shows, for moved row still where move starts; copy row marked for deletion is dropped copy; copy back onto the name its file is moving away from reads file once moved (`Wanted::copies_after`), and one whose moved row is marked, or that lands on row a put replaced, leaves file in place. `:ch` lists steps in order `:w` runs them (copies, deletions, renames and moves, copies back, folders), so it reads top to bottom. What comes to nothing leaves memory when write starts (`App::drop_no_ops`). `dd` keeps pending rename, dormant while row marked (`App::dormant`), so `p` moves file under new name. `y`, `dd` and `dd` in playlist share one register, as in vim, so `p` puts whichever came last; register keeps what it took (`Yanked`): follows its row through moves and undo, names that row only while row still shows file it took (`App::yanked_row`), `p` copies file row came from once undo, `:e!` or put took row away, and after move holds moved files, so another `p` copies them.
- **Each view tab keeps own cursor, scroll and sort**, snapshotted by `App::snapshot` on way out, restored on way back; state added to view must join `ViewTab` too or it leaks between tabs.
- **`unsafe` banned.** No `unsafe` block anywhere, and no dependency added to work around that. Music player has no performance problem justifying it; guarantee worth more than any optimisation it buys.
- **Crash or kill loses everything pending, intended.** No swap file, no journal: `:w` only writer, so force quit is valid way out of mess. Never add recovery file that makes kill leave changes behind.

## Invariants and gotchas
- **Open window owns keyboard, after ctrl-c.** `keys::handle` answers ctrl-c first, in every mode but `:` and `/` lines, edit mode included; then checks alert box, `show_info`, `show_changes`, `show_help`, `show_history` before dispatching on mode, else popup opened inside rename leaves its keys editing name behind it. Windows drawn above message row so that line stays readable under them.
- **Scans and `:w` run off input thread** (`app/jobs.rs`), spinner and count on statusline: navigation and playback keep working, every change waits until job lands (`App::busy`), because scan is about to replace every row and write is applying changes already queued. Scan replaces nothing until it lands (`App::adopt`), so unreadable library leaves open one as it was. Quitting does not wait for scan, and stops write between steps or copy chunks (`App::stop_jobs`). Scan before terminal is taken runs inline, with boot rows. Failure landing while window up waits for it to close (`App::alert_up`).
- **`:e!` clears whole pending set**, not just buffer being typed, puts every edited playlist back to what its file says, puts memory back without reading disk (pending move's track back at source, pending copy's row removed, row a put replaced back where its file is, replaced copy row not at all), then rereads library in background. `App::discard_changes` is the one place that must know every pending field. `:e`, `:set root=` and `:reload` refuse while anything pending, because pending is keyed to this library's rows.
- **lrclib entry's duration describes uploader's file, not its timestamps: may rank hit, never veto one.** Same timed lines come back claiming durations minutes apart, so hit seconds out is no evidence against its timings; never parse timestamps then throw them away on it, which also takes `[` and `]` off lines that need them. `lyrics::gap` orders candidates, nothing more. **`lyrics::runs_over` only thing that may cost sheet its timestamps**, because last line past track end cannot be about this recording and no single shift pulls it back. Hit gets that far only if artist and title agree with tags (`lyrics::close`): lrclib search matches substrings, so ranking on duration alone syncs wrong song of similar length.
- **Per-file lyric offset applies to timestamps, nothing else**, so `Fetcher::nudge` answers `None` on words without any and key says so on failed half of message row; never report `lyrics -7.0s` or write offset into cache while nothing on screen can move, since that is status claiming success that did not happen.
- **`demo/stage.sh` carries copy of `CACHE_MARK`**, because it seeds lyric cache so render never calls lrclib. Bumping constant in `src/lyrics.rs` without bumping it there leaves rig writing entries vibox refuses to trust, and lyrics shot renders empty.
- **Changing what cached lyric means means bumping `CACHE_MARK`.** Entry without current mark refetched, not trusted, so matching or parsing fix shipped without bump leaves everyone's wrong lyrics in place. Bumped by hand, never carries crate version: most releases do not touch lyrics, and refetching every library each release is neither fast for user nor fair on free api.
- **Nothing reaches disk until `:w`.** Renames, moves, copies, deletions, playlist edits and playlist deletions all sit in memory; `App::unsaved` drives `[+]` marker, `:changes` lists them, `App::start_write` applies them together. New mutation must join that path, not act immediately. Exceptions: `:mkdir` and `:mkplaylist`, made when typed.
- **Lyrics pane is third `Pane`, exists only while `:set lyrics` on.** `ctrl-w`, tab and page keys must never land on `Pane::Lyrics` with pane closed; `:set nolyrics` hands keyboard back to tracks. Scrolling by hand pins it (`lyrics_pinned`); renderer drops pin the moment focus leaves, so no new call site must remember to release it. `lyrics_h` and `lyrics_rows` written by renderer every frame like `track_h`, because only it knows how words wrapped.
- **Only a timestamp may move lyrics pane.** Page with no timings stays put and is scrolled by hand (`ctrl-w l`, then usual motions), nothing on it styled as current. Never scroll by `elapsed / duration`: words not spread evenly through song, so it runs ahead of vocals by intro length, and pane moving for reason user cannot see is worse than still one. Highlight is a claim, so is scroll position.
- **`gt` and `gT` act on focused pane:** sidebar flips `folders | playlists`, track pane walks open view tabs. `h` and `l` are seek keys and stay so, which is why tabs never took them.
- **Playlist is view over library, not new root.** `App::open_playlist` fills `playlist_rows`, leaves `root`, `tracks` and folders tab alone, so rewrite reopening root on every playlist breaks browsing while one is open. Entry naming moving file is row it moves to (`App::row_for`), else stray row duplicates it and save names path write empties. Folder view lists library rows only (`in_library`), so playlist's stray and missing rows never join a folder.
- **Playlist edit belongs to its file, not tab** (`App::pl_edits`): opening another view in same tab keeps it, `:ch` lists it, `:w` saves it, undo restores it into that playlist and no other. Playlists told apart by file everywhere (`playlist_view`, `ViewTab::playlist` and `Renaming::Playlist` are paths), since `mix.m3u` and `mix.m3u8` are two playlists with one name.
- **Write repairs every playlist naming file it renamed, moved or deleted** (`write::repair_all`, through `library::repair_m3u`), including library's own m3u when opened from one and playlist `:w <path>` wrote outside playlist folder (`App::elsewhere`, followed through folder renames), else renamed track silently vanishes from playlists referencing old path. Only changed entries rewritten: playlist names files outside library, files on unmounted drives and lines vibox does not read, so never rebuild it from `app.tracks`, which drops them all. m3u read as bytes, relative entries against its own folder; entry whose file is missing kept as own row (`library::missing`) so saving playlist does not drop it. Edited playlist saved same way (`library::save_m3u`): staying entries keep their lines, comments stay put, byte order mark stays, only what edit added or removed changes. Diff behind it (`library::kept_in_order`) stays linear in memory: playlist may name one track thousands of times. Repaired entry follows its file through steps that ran (`write::follow`), so write stopping partway repairs only what it did; edited playlist saved naming each row where write leaves it (`App::final_path`), so it drops tracks write deleted; playlist renamed in same write repaired and saved where it is now; copy joins library's own m3u. `:w <name>` names moved file where it is on disk now, for next `:w` to repair, and pending copy where it is going. Playlist repair cannot update is note after write, not stopped write.
- **When adding a key:** every binding lives under `keys/`, in file for its mode (`normal.rs`, `edit.rs` for name being renamed, `line.rs` for `:` and `/`, `windows.rs` while window up), shared vi text helpers in `text.rs`, dispatch in `mod.rs`. Multi-key sequences go through `app.pending` (one of `g`, `z`, `d`, `y`, `Z`, ctrl-w), consumed before counts read; count typed before prefix kept for key completing it (`5gg`, `3dd`); `KeyEventKind::Press` filter at top of `handle` mandatory, because kitty protocol terminals also send release events and every motion doubles without it.
- **When touching audio:** `player.rs` runs one thread owning both pulseaudio socket and decoder. UI sends `Cmd`s over channel, reads position, paused and finished from atomics. Never do blocking audio work on UI thread.
- **When changing pause:** pause is `CorkPlaybackStream`; corked stream gets no `Request` messages from server, so thread must block on command channel, not socket; reading socket while corked deadlocks until user resumes. Exception: answer already asked for comes promptly; drain does not finish while corked, so never counts as one.
- **Every request to sound server gets own tag** (`Wire::send`); its reply or error acts only on play it was for. Two plays can be in flight before first stream exists: fixed tag binds newer decoder to older stream at that stream's rate and leaks the other; deleting draining stream fails its drain, and treating that error as new track's discards new track. Reply for replaced play deletes its stream.
- **When changing seek or progress bar:** position is `base + (fed - inflight) / rate`, `inflight` being `write_offset - read_offset` from timing reply. Seek sends `FlushPlaybackStream`, dropping server buffer, so `fed` resets to 0 and `base` becomes seek target; forgetting either makes clock lie.
- **When touching decoding:** rodio is `default-features = false` with decoder features only; its `playback` feature pulls in cpal and alsa-sys and breaks no-system-headers rule.
- **When reading tags:** tag present but blank counts as absent, else row renders empty and file looks missing. Fallback is filename without extension, stored in `Track::file`.
- **Track list shows `Track::file`, not `Track::title`.** Tags fill artist and album columns, statusline and mpris metadata; filename is identity in list.
- **When changing track row** (`ui/tracks.rs`): `columns()` and header string must agree; fixed width is `gutter()`, one space after each visible column, and `duration_width()`.
- **When changing statusline:** only now-playing segment may stretch. Everything else fixed width, subtracted first, else large library gets last digit of track count clipped.
- **When changing layout:** `app.track_h` written by renderer every frame and paging keys depend on it; sticky header is separate one row area, subtracted from it.
- **`view` holds indices into `tracks`; `queue` is snapshot of `view` taken when playback starts.** So filtering or sorting never disturbs what plays; code assuming `queue` matches current view is wrong. Rescan invalidates all those indices, so `App::adopt` remembers playing track, queue, and rows of open playlist and every edited one as paths and looks them up again afterwards; else audio thread plays track statusline calls `not playing`. Everything else changing `tracks` (sort, put, deletion, undoing copy) goes through `App::retarget`, one place knowing every index holder: view, queue and positions into it, `playing`, open playlist and every edited one (`pl_edits`), pending renames (`Renaming::Track` is an index), name being typed. New index holder joins it there, else sort renames wrong file. Undo snapshots hold no index: they name rows by path each has at that moment (`Held`), and stepping to one puts every row back where it was before those paths are looked up (`App::apply_pending`), because rows leave list and return between snapshots and index then means another row. `p` refuses name another row keeps after `:w`, because two rows with one path cannot be told apart by anything finding row by path. Row marked for deletion gives up its name by leaving list (`App::land_on`, into `replaced` with file it showed: that file deleted first on `:w`, undo brings row back); row with rename waiting takes new name at once, refused while another row keeps it (`App::holder_stuck`); row marked for deletion on it gives it up the same way. Playing track whose row leaves list stays on statusline (`playing_gone`), since sound thread still plays it, and gets its row back when undo brings row back. Rescan finds playing row by file sound thread plays (`playing_file`, followed through write), never by row's path, which may name pending destination. Entry leaving queue hands its place to one before it, so next stays one after, and with none before, `qpos` is next itself (`qpos_next`).
- **When touching mpris:** `mpris.rs` claims `org.mpris.MediaPlayer2.vibox`, falls back to instance suffixed name so second process still starts. UI publishes snapshot from `App::tick`; watcher thread diffs it and emits PropertiesChanged, because desktop widgets update off signal and never poll.
- **Degrade, never abort:** `App::audio` and `App::mpris` both `Option`. No audio device or no session bus: vibox still browses, every affected key reports one line on message row.
- **Never enable mouse capture.** It takes selection and scrollback from terminal and tmux.
- **Library opened from m3u keeps own order:** `library::scan` skips path sort for playlists, `App::adopt` and `App::resort` skip re-sorting when sort key is default (`keeps_its_own_order`); rewrite of any of them must preserve that. Its folder list is folders its tracks sit in, never walk of m3u's folder.
- **When touching search:** haystack is row's columns only. Including path makes every track under directory match its name (`/testing` inside `TESTING/` matches all).
- Terminal check in `main` keeps raw OS error off screen: without it ratatui panics with `Os { code: 6 }` when stdout not tty.

## Build / lint / test
- `cargo build --release`, binary at `target/release/vibox`.
- `cargo +1.89 msrv` checks crate against advertised `rust-version` floor (alias in `.cargo/config.toml`); when code needs newer compiler, floor and toolchain in this line move together.
- Test builds its `App` with `App::offline`: never reaches sound server or session bus, keeps playlists in test's own directory; `App::new` would claim media keys on bus of whoever runs suite.
- Run release binary against scratch directory of audio files: `./target/release/vibox <dir>`.
- `demo/` is source of `readme-assets/demo.gif`, README's one image, committed for that reason (package `exclude`s it). Gif only asset, so `demo.tape` only tape: no stills tape, since files nothing links to are churn every release. `demo/stage.sh up` builds staged `HOME`: library of invented bands, silent audio encoded by ffmpeg, seeded playlists, seeded lyric cache. `demo/render.sh` renders tour gif in container whose image adds pulseaudio; each tape runs with no network, and container starts pulseaudio with null sink before vhs (playback must really run, else clock, progress bar and lyrics never move), then stages, records and tears down. `./stage.sh down` deletes stage. Re-stage between tapes: `demo.tape` types `:w` and really renames fixtures. Fixtures are silence, render makes no noise: `:matrix` only thing needing real amplitude to draw, and it is easter egg with no shot and no beat in any tape, so nothing on screen depends on output loudness. Fixtures get real tone only together with a `:matrix` shot.
- `cargo run --example boot -- 5` replays boot rows (braille wordmark decoding above scan progress line) against made up scan; warm page cache means real library almost never exceeds `GRACE`, so otherwise no way to look at them. Tests in `src/boot.rs` assert escape codes those rows write.
- Check mpris surface while it runs: `busctl --user call org.mpris.MediaPlayer2.vibox /org/mpris/MediaPlayer2 org.mpris.MediaPlayer2.Player PlayPause`, and `busctl --user get-property org.mpris.MediaPlayer2.vibox /org/mpris/MediaPlayer2 org.mpris.MediaPlayer2.Player Metadata`.

## Overview
**Crate is library with thin binary on top.** `src/lib.rs` owns every module and `src/main.rs` is argv parsing plus event loop, because binary target cannot be imported: `tests/` and `examples/` reach only code in lib. Anything worth testing or demonstrating goes in lib; reaching into binary through environment variable is no substitute.
Layout:
- `src/ui/widgets.rs` is pane furniture knowing nothing of domain; keep track, playlist and folder knowledge out of it.
- io errors reach screen as words through `reason::of`, never as raw OS error.
- No `tui/` module: vibox is one interface, so terminal setup a multi-screen crate would share lives in `main.rs`.

`vibox` is Rust TUI music player, AGPL-3.0-only: jukebox you exit with `:q`. Library is directory (or m3u), track is file, interface modal in vi sense, lyrics as third pane. Linux only for now; output layer is only platform specific part.
