# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the rules, invariants and gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- **Where the colours land in vibox.** The line under the panes is `app.info` (green, it worked) and `app.error` (yellow, it did not), both on the same three-second `MSG_TTL` through `App::live_msg`; nothing there is ever red, and nothing in the statusline is either. The one red in the app is the `Mode::Edit` indicator, and a gate would be the other if one is ever added.
- **Never add a dependency that needs a C library, system headers, or an external binary.** `cargo install vibox` must succeed on a bare toolchain; a build that fails on a missing header is a broken product. This is why the audio output is written against the pulseaudio wire protocol instead of using cpal.
- **The published crate has a lib target, and that lib is not a public API.** The split exists so `tests/` and `examples/` can reach the code, not so anyone can depend on `vibox` as a library. Nothing outside this repo is expected to `use vibox::...`, so a `pub` item moving or changing shape is not a breaking change and does not need a major bump. Do not start treating module paths as a contract.
- **vibox never retags a track, and touches a music folder only in the ways the user asked for:** a rename typed in the edit buffer, a move, a copy, a delete or a `:mkdir`. Everything else about a library is read only. The README promises this across three sections (`Rename files in place`, `Nothing is written until :w`, `Changing the library itself`), so a feature that widens it without widening those is a lie in the documentation as well as a bug.
- **There is no arming switch in front of a file operation, and adding one back would be a mistake.** `:set danger` used to gate `dd`, `d`+`p`, `y`+`p` and `:mkdir`, and it was removed because the staging already does that job better: nothing touches the disk when the key is pressed, `:ch` lists exactly what is waiting, `u` and `:e!` undo it, and `:q` refuses while anything is pending, so the only way to lose a file is to read the change and type `:w`. A mode you set once and forget you are in protects nothing that a change you can read before writing does not already protect - and it cost a statusline flag, a persisted option that must never come back on its own, and a set of refusals that named the mode instead of the reason. If a stronger guard is ever wanted, it goes at the moment of the destructive commit (a red gate on a `:w` that deletes), never back into a mode.
- **An option the app does not have is skipped, not fatal.** `:set` reports an unknown name and carries on with the rest of the line, so one stale word in an rc file (`set danger`, which existed until it did not) cannot cost you the options written beside it; `load_rc` clears the message afterwards, so the file talking is silent and a person typing is not.
- **`:w` is planned before it is applied** (`app::plan`, entered through `App::write_plan`): renames, moves, copies and deletions are checked together as one namespace, because per-kind checks each saw only their own list, which both refused a rename onto a name a deletion was about to free and allowed a rename and a move to claim one name, where `fs::rename` overwrote one with the other silently. **occupied** is asked of the filesystem and never of `app.tracks` (tracks holds only audio, so a tracks-based check would clobber `cover.jpg`, and on a case-insensitive mount `song.mp3` and `SONG.mp3` are one file but two strings); the in-memory sets may only excuse a clash, never invent one. Deletions run first because they are what frees a name, renames are ordered so none lands on a name still in use, and a cycle (a swap) is refused rather than given a temporary name. Every `fs::rename` is also guarded immediately before the call, since the plan is a moment old and `fs::rename` overwrites without asking; closing the last microsecond of that window needs `renameat2`, which needs libc and `unsafe`, so it stays open and documented.
- **A typed name is checked before any of the batch runs** (not empty, no `/`, since this renames and never moves), so a bad name aborts the whole write instead of leaving a folder half renamed. Whether the name is *free* is not this check's job but the plan's above, which is the only thing that can see the deletions and moves that free one.
- **Each view tab keeps its own cursor, scroll and sort**, snapshotted by `App::snapshot` on the way out and restored on the way back; state added to the view must be added to `ViewTab` too or it leaks between tabs.
- **`unsafe` is banned.** vibox must build with no `unsafe` block anywhere, and no dependency may be added to work around that. A music player has no performance problem that justifies it, and the guarantee is worth more than any optimisation it would buy.
- **A crash or a kill loses everything pending, and that is intended.** There is no swap file and no journal: `:w` is the only thing that writes, so force quitting is a valid way out of a mess. Never add a recovery file that would make a kill leave changes behind.

## Invariants and gotchas
- **An open window owns the keyboard.** `keys::handle` checks `show_info`, `show_changes` and `show_help` before it dispatches on mode, or a popup opened from inside a rename leaves its keys editing the name behind it.
- **`:e!` clears the whole pending set**, not just the buffer being typed, and rescans afterwards so rows hidden by a cut come back. `App::discard_changes` is the one place that has to know every pending field.
- **An lrclib entry's duration describes the uploader's file, not its timestamps, so it may rank a hit and must never veto one.** The same twenty timed lines come back claiming anything from 4:23 to 6:58 (`Ice Cube - Gangsta Rap Made Me Do It`, checked against the api), so a hit seven seconds out is no evidence at all against its timings, and vibox used to answer that non-evidence by parsing the timestamps and then throwing them away, which also took `[` and `]` off the one track that needed them. `lyrics::gap` orders candidates and nothing more. **`lyrics::runs_over` is the only thing that may ever cost a sheet its timestamps**, because a last line falling past the end of the track cannot be about this recording and no single shift can pull it back. A hit only gets that far if its artist and title agree with the tags (`lyrics::close`): lrclib's search matches substrings, so ranking on duration alone once synced `Nightmares on Wax - Date With Destiny` onto a track called `Wax - Destiny`.
- **A per-file lyric offset applies to timestamps and to nothing else**, so `Fetcher::nudge` answers `None` on words that never had any and the key says so on the failed half of the message row. It used to report `lyrics -7.0s` and write the offset into the cache while nothing on screen could move, which is a status line claiming something worked when it did not.
- **`demo/stage.sh` carries a copy of `CACHE_MARK`**, because it seeds the lyric cache so a render never calls lrclib. Bumping the constant in `src/lyrics.rs` without bumping it there leaves the rig writing entries vibox refuses to trust, and the lyrics shot renders empty.
- **Changing what a cached lyric means means bumping `CACHE_MARK`.** An entry without the current mark is refetched instead of trusted, so a fix to matching or to parsing that ships without the bump leaves everyone's wrong lyrics exactly where they were. The mark is bumped by hand and never carries the crate version: most releases do not touch lyrics, and refetching every library on every release is neither fast for the user nor fair on a free api.
- **Nothing reaches the disk until `:w`.** Renames, playlist edits and playlist deletions all sit in memory, `App::unsaved` drives the `[+]` marker, `:changes` lists them and `App::write_all` applies them together. A new mutation must join that path rather than acting immediately.
- **The lyrics pane is a third `Pane`, and it only exists while `:set lyrics` is on.** `ctrl-w`, tab and the page keys must never land on `Pane::Lyrics` with the pane closed, and `:set nolyrics` hands the keyboard back to the tracks. Scrolling it by hand pins it (`lyrics_pinned`), and the pin is dropped by the renderer the moment the focus leaves, so no new call site has to remember to release it. `lyrics_h` and `lyrics_rows` are written by the renderer every frame the way `track_h` is, because only it knows how the words wrapped.
- **Only a timestamp may move the lyrics pane.** A page with no timings is left where it is and scrolled by hand (`ctrl-w l`, then the usual motions), and nothing on it is styled as current. Scrolling it by `elapsed / duration` instead was tried and removed: the words are not spread evenly through a song, so it ran ahead of the vocals by the length of the intro, and a pane that moves for a reason the user cannot see is worse than one that sits still. A highlight is a claim, and so is a scroll position.
- **`gt` and `gT` act on the focused pane:** the sidebar flips `folders | playlists`, the track pane walks the open view tabs. `h` and `l` are seek keys and must stay that way, which is why tabs never took them.
- **A playlist is a view over the library, not a new root.** `App::open_playlist` fills `playlist_rows` and leaves `root`, `tracks` and the folders tab alone, so a rewrite that reopens the root on every playlist would break browsing while one is open.
- **A rename rewrites every playlist that named the file** (`App::repair_playlists`), otherwise a renamed track silently disappears from playlists that reference the old path.
- **When adding a key:** every binding lives under `keys/`, in the file for the mode it belongs to (`normal.rs`, `edit.rs` for a name being renamed, `line.rs` for `:` and `/`, `windows.rs` while a window is up), with the shared vi text helpers in `text.rs` and the dispatch in `mod.rs`. Multi-key sequences go through `app.pending` (one of `g`, `z`, `d`, `y`, `Z`, ctrl-w) and are consumed before counts are read; the `KeyEventKind::Press` filter at the top of `handle` is mandatory, because terminals speaking the kitty protocol also send release events and every motion doubles without it.
- **When adding a key, do not require a prefix for anything ordinary.** vibox is expected to run inside tmux, so a binding that needs a leader or a `ctrl-b` style chord fights the multiplexer; single presses and vi sequences only.
- **When touching audio:** `player.rs` runs one thread that owns both the pulseaudio socket and the decoder. The ui sends `Cmd`s over a channel and reads position, paused and finished out of atomics. Never do blocking audio work on the ui thread.
- **When changing pause:** pause is `CorkPlaybackStream`, and a corked stream gets no `Request` messages from the server, so the thread must block on the command channel and not on the socket; reading the socket while corked deadlocks until the user resumes.
- **When changing seek or the progress bar:** position is `base + (fed - inflight) / rate`, where `inflight` is `write_offset - read_offset` from the timing reply. A seek sends `FlushPlaybackStream`, which drops the server buffer, so `fed` resets to 0 and `base` becomes the seek target; forgetting either makes the clock lie.
- **When touching decoding:** rodio is `default-features = false` with decoder features only. Enabling its `playback` feature pulls in cpal and alsa-sys and breaks the no-system-headers rule.
- **When reading tags:** a tag that is present but blank counts as absent, otherwise the row renders empty and the file looks missing. The filename without its extension is the fallback and is stored in `Track::file`.
- **The track list shows `Track::file`, not `Track::title`.** Tags fill the artist and album columns, the statusline and the mpris metadata; the filename is the identity in the list.
- **When changing the track row** (`ui/tracks.rs`): `columns()` and the header string must stay in agreement, and the fixed width is 10 columns plus whatever `duration_width()` returns (7 once anything in view runs past an hour, 5 otherwise).
- **When changing the statusline:** only the now-playing segment may stretch. Everything else is fixed width and must be subtracted first, or a large library gets the last digit of its track count clipped.
- **When changing the layout:** `app.track_h` is written by the renderer every frame and the paging keys depend on it; the sticky header is a separate one row area and must be subtracted from it.
- **`view` holds indices into `tracks`; `queue` is a snapshot of `view` taken when playback starts.** Filtering or sorting therefore never disturbs what is playing, and code that assumes `queue` matches the current view is wrong. A rescan invalidates every one of those indices, so `reload_reporting` remembers the playing track and the queue as paths and looks them up again afterwards; dropping them instead left the audio thread playing a track the statusline called `not playing`.
- **When touching mpris:** `mpris.rs` claims `org.mpris.MediaPlayer2.vibox` and falls back to an instance suffixed name so a second process still starts. The ui publishes a snapshot from `App::tick`; a watcher thread diffs that snapshot and emits PropertiesChanged, because desktop widgets update off the signal and never poll.
- **Degrade, never abort:** `App::audio` and `App::mpris` are both `Option`. No audio device or no session bus means vibox still browses, and every affected key reports one line on the message row.
- **Never enable mouse capture.** It takes selection and scrollback away from the terminal and from tmux.
- **Playlists are read only for now:** `:e` opens an m3u and it keeps its own order. `library::scan` skips the path sort for playlists and `App::reload` skips re-sorting when the sort key is the default, so a rewrite of either must preserve that.
- **When touching search:** the haystack is the columns of the row only. Including the path made every track under a directory match that directory's name, so `/testing` inside `TESTING/` matched all of them.
- The terminal check in `main` is what keeps a raw OS error off the screen here: without it ratatui panics with `Os { code: 6 }` when stdout is not a tty.

## Build / lint / test
- `cargo build --release`, binary at `target/release/vibox`.
- `cargo +1.89 msrv` checks the crate against the `rust-version` floor it advertises (alias in `.cargo/config.toml`), and when the code starts needing a newer compiler both that floor and the toolchain in this line move together.
- Run the release binary against a scratch directory of audio files: `./target/release/vibox <dir>`.
- `demo/` is the source of `readme-assets/demo.gif`, the one image in the README, and it is committed for that reason (the package `exclude`s it). The gif is the only asset, so `demo.tape` is the only tape: anything it already shows does not get a screenshot as well, and a stills tape that renders files nothing links to is churn on every release. `demo/stage.sh up` builds a staged `HOME` with a library of invented bands, silent audio encoded by ffmpeg, seeded playlists and a seeded lyric cache; `vhs demo.tape` renders the tour gif; `./stage.sh down` deletes the stage. Re-stage between tapes: `demo.tape` types `:w` and really renames the fixtures. The fixtures are silence and a render makes no noise: `:matrix` is the only thing that ever needed real amplitude to draw, and it is an easter egg with no shot and no beat in any tape, so nothing on screen depends on how loud the output is. Do not put a tone back in without putting a `:matrix` shot back too.
- `cargo run --example boot -- 5` replays the boot rows (the braille wordmark decoding above the scan progress line) against a made up scan. A warm page cache means a real library almost never takes longer than `GRACE`, so there is otherwise no way to look at them. `tests/boot.rs` asserts the escape codes those rows write.
- Check the mpris surface while it runs: `busctl --user call org.mpris.MediaPlayer2.vibox /org/mpris/MediaPlayer2 org.mpris.MediaPlayer2.Player PlayPause`, and `busctl --user get-property org.mpris.MediaPlayer2.vibox /org/mpris/MediaPlayer2 org.mpris.MediaPlayer2.Player Metadata`.

## Overview
**The crate is a library with a thin binary on top.** `src/lib.rs` owns every
module and `src/main.rs` is argv parsing plus the event loop, because a binary
target cannot be imported: `tests/` and `examples/` can only reach code that
lives in the lib. Anything worth testing or demonstrating goes in the lib, and
reaching into the binary through an environment variable is not a substitute.
Layout:
- `src/main.rs` - argv parsing, terminal setup and the event loop, nothing else.
- `src/app/` - all state, split by concern (`playlists`, `rename`, `plan`, `files`, `scan`, `tabs`, `undo`, `cursor`, `select`, `search`, `playback`), with `mod.rs` owning `App` itself.
- `src/keys/` - key dispatch in `mod.rs`, then one file per mode plus `text.rs` for the vi text helpers the rename buffer and the command line share.
- `src/ui/` - rendering split by what is on screen: `folders`, `tracks`, `status`, `popups`, `lyrics`, with `widgets.rs` for pane furniture that knows nothing about the domain and `name_diff.rs` for the character diff a rename shows.
- Domain modules at the top level: `library`, `player`, `mpris`, `lyrics`, `name`, `excmd`, `boot`, `matrix`, `selfcmd`.
- There is no `tui/` module: vibox is one interface, so the terminal setup that a multi-screen crate would share lives in `main.rs`.

`vibox` is a Rust TUI music player, AGPL-3.0-only: a jukebox you exit with `:q`. The library is a directory (or an m3u), a track is a file, and the interface is modal in the vi sense: normal, visual, search and ex command modes, vi motions with counts, `/` and `:` on the last screen line, and a two pane layout of folders and tracks. `src/app/` holds all state and the playback queue, `keys.rs` the keymap, `excmd.rs` the `:` commands, `ui.rs` the rendering, `library.rs` the scan and the tag reading, `boot.rs` the rows drawn while it scans, `player.rs` decoding and pulseaudio output, `mpris.rs` the d-bus interface that makes media keys work. Linux only for now; the output layer is the only platform specific part.
